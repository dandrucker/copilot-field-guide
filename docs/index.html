Guide 0

Teach Copilot your codebase once, not every prompt.

Out of the box, Copilot knows programming. It doesn't know your repo, your conventions, your pipelines or your budget. These guides show you how to close that gap with a few small Markdown files, and how to do it without burning through AI credits.

The mental model

Every customization is just Markdown that gets placed into the model's context. What differs is when it gets loaded. Things that load on every request cost tokens on every request, so they should be small. Things that load on demand can be large.

Project instructions
.github/copilot-instructions.md or AGENTS.md. Loaded on every chat request in the repo. Keep it short.
Scoped instructions
*.instructions.md with applyTo. Loaded only when Copilot touches matching files.
Skills
SKILL.md folders. Only the name and description sit in context until the task calls for the rest.
Custom agents
*.agent.md. You switch to them (or another agent delegates to them). They change instructions, tools and model together.
Reference docs
Files like DESIGN.md that instructions or skills point to, read when relevant.

Always loaded Loaded by file match Loaded on demand

The route

Work through these in order the first time. After that, use them as reference.

  • 2Instructions and AGENTS.mdWrite the rules Copilot follows in every session.
  • 3Custom agentsBuild a planner, reviewer or implementer with its own tools and model.
  • 4Agent skillsPackage a repeatable procedure with scripts and templates.

Before you start

  • VS Code, current stable release, signed in with the GitHub account that holds your Copilot seat.
  • A repository you can experiment in. Customization files are plain Markdown, committed like any other code, and reviewed in pull requests.
  • Know which Copilot plan you're on. Business and Enterprise seats draw from a shared organization pool, so your habits affect your teammates.

Guide 1

Using GitHub Copilot in VS Code

Copilot shows up in several places in the editor. Knowing which surface fits the job is the first and cheapest optimization you can make.

Set up

  1. Install VS Code and sign in with GitHub (Accounts menu, bottom left). Copilot is built into current releases; if prompted, install the GitHub Copilot Chat extension.
  2. Confirm the Copilot icon in the Status Bar shows you as signed in. Clicking it opens the status dashboard, including your monthly usage.
  3. Open a folder that is a Git repository. Much of Copilot's grounding comes from the workspace index, which respects .gitignore.
  4. Open Workspace Trust for the folder if asked. Agents run terminal commands and hooks only in trusted workspaces.

The four surfaces

SurfaceHow you get thereUse it for
Inline suggestions and next edit suggestionsJust type. Tab accepts, Esc dismisses.Finishing the line or block you're writing, and the obvious follow-on edit. On paid plans these don't consume AI credits.
Inline chatCtrl+I in the editorA focused change to the selection: "add null checks", "convert to async".
Chat viewCtrl+Alt+IQuestions, planning, and agent sessions that edit multiple files and run commands.
Agents windowView menu or Command PaletteManaging several sessions at once, including background and remote sessions.

Custom instructions don't affect inline suggestions. They apply to chat and agent sessions only. If completions ignore your conventions, that's expected.

Agents, roles and harnesses

In the Chat view you pick an agent from the dropdown. The built-in roles cover the common cases. Plan researches and produces an implementation plan without editing; the default Agent role edits files, runs terminal commands and iterates until the task is done. Your own custom agents appear in the same dropdown (guide 3).

The Session Target control picks the harness that runs the session, such as Copilot or the Local agent. The harness decides which customization files are discovered, so if a file seems to be ignored, check the harness first.

Give it the right context

Most bad answers come from missing or excessive context. Point Copilot at exactly what matters.

Type thisWhat it does
#file, or drag a file into chatAttach a specific file.
#codebaseGround the request in the semantic index of the workspace.
#tool:<name>Reference a specific tool, for example a fetch or MCP tool.
/Lists prompt files and skills you can run as commands.
/initGenerate project-wide instructions from the repo (guide 2).
/compactSummarize older turns to reclaim context space.
/forkBranch the session to try an alternative without losing the original.

A good agent prompt names the goal, the files, the constraints and how to verify:

prompt
Add retry with exponential backoff to the pipeline status client in
#file:src/clients/statusClient.ts. Max 3 retries, only on 429 and 5xx.
Follow the existing logger pattern. Add unit tests next to the client,
then run `npm test -- statusClient` and fix any failures.

Work in sessions

  • One task per session. Start a new session (Ctrl+N in the Chat view) when you change topics. Old history is re-sent with every turn.
  • Plan first for anything non-trivial. Use the Plan agent, correct the plan, then hand off to implementation.
  • Review every change. Edits appear as diffs you keep or undo per file. Checkpoints let you roll the session back to an earlier point.
  • Read approvals. Terminal commands and sensitive tools ask before running. Auto-approve only commands you'd run unattended.

Customizations live in one place

Run Chat: Open Customizations (or the gear icon in the Chat view) to open the Agent Customizations editor. It lists the instructions, agents, skills, prompts, hooks and MCP servers the selected harness can see, and has shortcuts to create or generate each one. It's the first place to look when something isn't being picked up.

If your repositories are in Azure Repos. Everything in these guides that runs inside VS Code works regardless of where your Git remote is hosted: chat, agent sessions, instructions, custom agents, skills and hooks. Features that run on github.com, such as the Copilot cloud agent working from issues and Copilot code review on pull requests, need the repository to be hosted on GitHub.

Guide 2

Instructions and AGENTS.md

Instructions are the rules Copilot should follow without being told: your stack, your structure, how to run tests. Written once, committed to the repo, applied to everyone.

The three instruction files

FileWhereWhen it loadsBest for
copilot-instructions.md.github/Every chat request in the repoProject-wide rules for Copilot
AGENTS.mdRepo root (optionally nested in subfolders)Every request, for harnesses that support itThe same rules shared across several AI tools
*.instructions.md.github/instructions/ (searched recursively)When applyTo matches a file being changed, or when the description fits the taskLanguage, folder or file-type rules

AGENTS.md is an instructions file, not an agent. Despite the name, it doesn't create anything in the agents dropdown. It's a cross-tool convention for project guidance that Copilot, Codex and other agents all read. Custom agents are .agent.md files, covered in guide 3.

Pick one of copilot-instructions.md or AGENTS.md as your primary file. If you keep both, make sure they don't contradict each other: instruction sources are additive and there's no reliable precedence rule.

Write the project file

The fastest start is /init in chat, which analyzes the repo and drafts a file. Treat the draft as a first pass: verify every command and path it wrote. A good project file is short and concrete.

.github/copilot-instructions.md
# Project instructions

## Stack
* .NET 8 Web API in `src/Api`, React 18 + TypeScript in `src/Web`.
* Data access through EF Core repositories in `src/Api/Data`. No raw SQL in controllers.

## Conventions
* Use `ILogger<T>` structured logging. Never log connection strings or tokens.
* Prefer `date-fns` over `moment` because moment is deprecated and bloats the bundle.

## Validate your work
* Backend: `dotnet test` from the repo root.
* Frontend: `npm test -- --run` in `src/Web`.
* Every behavior change needs a test.

## Don't
* Don't edit files under `src/Api/Migrations` by hand.
* Don't add new NuGet or npm packages without saying why in the summary.

Scope rules to files with applyTo

Anything that only matters for part of the codebase belongs in a scoped file, so it costs nothing when Copilot is working elsewhere.

.github/instructions/frontend/react.instructions.md
---
name: 'React components'
description: 'Use when creating or editing React components or hooks.'
applyTo: 'src/Web/**/*.tsx'
---
# React conventions
* Function components only. Co-locate tests as `Component.test.tsx`.
* Styling comes from tokens in [DESIGN.md](../../../DESIGN.md). Never hard-code hex colors.
* Use React Query for server state; don't store fetched data in useState.
FrontmatterMeaning
applyToGlob, relative to the workspace root. Auto-attaches when a matching file is created or modified. ** matches everything.
descriptionLets the agent load the file on demand when the task matches, even without a file match.
nameDisplay name in the UI. Defaults to the file name.

With neither applyTo nor description, the file loads only when you attach it manually.

Use AGENTS.md when you run more than one agent

If some of your team use Copilot and others use Codex, Claude Code or another agent, a root AGENTS.md gives everyone one source of truth. In a monorepo, nested AGENTS.md files in subfolders can carry folder-specific guidance. For the Local agent this is behind the chat.useNestedAgentsMdFiles setting and is currently experimental; scoped .instructions.md files achieve the same result today.

Writing instructions that work

  • One rule per line. Short, self-contained statements beat paragraphs.
  • Say why. A reason lets the model handle edge cases the rule didn't anticipate.
  • Show code. A preferred-versus-avoided example is more effective than an abstract rule.
  • Skip what linters enforce. Spend the words on the non-obvious.
  • Include the validation commands. This is the single highest-value line in most files.
  • Link, don't paste. Point to longer docs with Markdown links; relative paths resolve from the instructions file.

Verify it's being used

  1. Open the Agent Customizations editor and confirm the file is listed for your harness.
  2. Start a new session and ask for a small task where the rule matters.
  3. Expand References under the response to confirm the file was included.
  4. Still missing? Run Developer: Open Agent Debug Logs to see discovery errors.

Other places instructions can come from. Personal instructions (your user profile or ~/.copilot/) and organization instructions set in GitHub are added on top of the repo's. Commit messages, PR descriptions and review-selection prompts each have their own github.copilot.chat.*.instructions setting.

Guide 3

Custom agents

A custom agent bundles instructions, a tool set and optionally a model into a role you switch to. A read-only reviewer, a planner, a migration specialist: each is one .agent.md file.

When an agent is the right tool

Reach for a custom agent when a recurring task needs a different configuration, not just different words. The strongest reasons are:

  • Restricting tools. A reviewer or planner that physically can't edit files.
  • Pinning a model. A cheap, fast model for bounded work; a stronger one for planning.
  • Chaining stages. Plan, then implement, then review, with a button between each.
  • Delegation. A coordinator that hands focused work to subagents with their own clean context.

If you only need more knowledge, use instructions or a skill instead.

Where agent files live

ScopeLocation
Workspace, shared with the team.github/agents/
Workspace, Claude format.claude/agents/
Just you, every workspace~/.copilot/agents/ or ~/.claude/agents/

Create one with Chat: New Custom Agent, or describe the role on the Overview page of the Agent Customizations editor and let it generate the file. If you have old .chatmode.md files, rename them to .agent.md; chat modes became custom agents.

Anatomy of an agent file

.github/agents/reviewer.agent.md
---
name: Reviewer
description: Review the current changes for correctness and our conventions. Never edits.
tools: ['search/codebase', 'search/usages', 'read/terminalLastCommand']
model: ['Claude Sonnet 5', 'GPT-5.6 Terra']   # tried in order
handoffs:
  - label: Fix findings
    agent: agent
    prompt: Fix the blocking findings from the review above.
    send: false
---
# Review instructions
You review code. You do not edit files.

For each finding, give: file and line, severity (blocking / should-fix / nit),
what's wrong, and a suggested fix.

Check, in this order:
1. Correctness and error handling
2. Security: secrets, injection, authorization checks
3. Tests: is new behavior covered?
4. Conventions in [copilot-instructions.md](../copilot-instructions.md)

End with a one-line verdict: approve, or request changes.
FieldWhat it does
name, descriptionShown in the dropdown and as input placeholder. Name defaults to the file name.
toolsThe only tools the agent can use. Built-in tools, tool sets, MCP tools, or server/* for a whole MCP server. Unavailable tools are ignored.
modelOne model, or a list tried in order. Omit to use whatever's selected in the picker.
handoffsButtons shown after a response that switch to another agent with a prefilled prompt. send: true auto-submits.
agentsWhich agents this one may call as subagents. Requires the agent tool in tools.
user-invocablefalse hides it from the dropdown but keeps it available as a subagent.
disable-model-invocationtrue stops other agents from calling it as a subagent.
targetvscode or github-copilot.
hooks (preview)Shell commands that run at lifecycle points only while this agent is active (Local harness).

Model names change. The model names in these examples were valid when written. Check the model picker for the exact names your organization has enabled.

Build a plan → implement → review pipeline

Handoffs turn separate agents into a workflow where you approve each stage. This is also the cheapest pattern for large tasks: a strong model plans once, cheaper models do bounded implementation.

.github/agents/planner.agent.md
---
name: Planner
description: Research the codebase and write an implementation plan. No edits.
tools: ['search/codebase', 'search/usages', 'web/fetch']
handoffs:
  - label: Implement plan
    agent: Implementer
    prompt: Implement the plan above, one step at a time. Run tests after each step.
---
Produce a plan with: Overview, Requirements, Files to change, Steps, Tests.
Flag anything ambiguous as a question instead of guessing.
.github/agents/implementer.agent.md
---
name: Implementer
description: Implement an approved plan with minimal, focused edits.
tools: ['edit', 'search/codebase', 'read/terminalLastCommand']
handoffs:
  - label: Review changes
    agent: Reviewer
    prompt: Review the changes made in this session.
---
Follow existing patterns. Don't refactor code the plan doesn't mention.

Coordinators and subagents

A subagent runs in its own context window and returns only its result. That keeps the main session lean. Use it when a subtask reads a lot of files but only its conclusion matters.

.github/agents/feature-builder.agent.md
---
name: Feature Builder
description: Research first, then implement.
tools: ['agent']
agents: ['Researcher', 'Implementer']
---
1. Ask the Researcher agent for relevant patterns and files.
2. Give its findings to the Implementer agent to make the change.

Delegation isn't free. Each subagent call has its own setup cost in tokens. Keep small tasks in the main session; delegate when isolation or a cheaper model clearly pays for the overhead.

Share and secure

  • Commit workspace agents to .github/agents/ and review them like code. A changed tools list is a permissions change.
  • Give each agent the fewest tools it needs. Read-only agents for anything security-sensitive.
  • Organization-level agents defined in GitHub appear for everyone when github.copilot.chat.organizationCustomAgents.enabled is on.
  • Treat shared agents from outside your organization like any third-party code: read them before use.

Guide 4

Agent skills

A skill is a folder containing a SKILL.md and whatever it needs: scripts, templates, examples. Copilot keeps only its one-line description in view and loads the rest when a task calls for it.

Why skills

  • Cheap until used. Dozens of skills cost roughly the size of their descriptions until one is needed.
  • They carry assets. A script that does the deterministic part, a template the output must follow.
  • They're portable. Agent Skills is an open standard. The same folder works in Copilot in VS Code, Copilot CLI and the Copilot cloud agent, and in other skills-compatible agents.

How Copilot loads a skill

  1. Discovery. Copilot reads every skill's name and description. Your request is matched against the descriptions.
  2. Instructions. For a matching skill, the body of SKILL.md is loaded into context. Typing /skill-name forces this step.
  3. Resources. Files in the folder are read only when the instructions reference them. Unreferenced files are never loaded.

The description is the trigger. Write what the skill does and when to use it, in the words a developer would actually type. A vague description means the skill never fires.

Where skills live

ScopeLocations
Project (committed).github/skills/, .claude/skills/, .agents/skills/
Personal~/.copilot/skills/, ~/.claude/skills/, ~/.agents/skills/

Build one

Type /create-skill and describe it, or use New Skill in the Agent Customizations editor. You can also finish a long debugging session with "create a skill from how we just debugged that".

folder layout
.github/skills/
└── pipeline-failure-triage/
    ├── SKILL.md
    ├── summarize-log.ps1
    └── report-template.md
.github/skills/pipeline-failure-triage/SKILL.md
---
name: pipeline-failure-triage
description: Triage a failed CI build. Use when asked why a build or pipeline failed,
  to read build logs, or to fix a red pipeline.
argument-hint: [path to downloaded log]
---
# Pipeline failure triage

## Steps
1. Run [summarize-log.ps1](./summarize-log.ps1) on the log file. It prints only
   error lines and the 20 lines before each, so you don't read the whole log.
2. Classify the failure: compile, test, dependency restore, infrastructure, or flaky.
3. For compile and test failures, find the code and propose a fix.
4. For infrastructure or flaky failures, don't change code. Say so and stop.
5. Write the result using [report-template.md](./report-template.md).

## Don't
* Don't paste full logs into the conversation.
* Don't retry the build yourself.

nameYesLowercase letters, numbers, hyphens; max 64 characters; must match the folder name. No slashes, colons, dots or org/ prefixes. A bad name makes the skill silently fail to load.
descriptionYesWhat it does and when to use it. Max 1024 characters.
argument-hintNoHint shown when used as a slash command.
user-invocableNofalse hides it from the / menu; Copilot can still auto-load it.
disable-model-invocationNotrue means it only runs when you type the slash command.

Reference bundled files with relative Markdown links or #file:./name, using forward slashes so the skill works on every OS.

Invoking skills

ConfigurationSlash commandAuto-loadedTypical use
DefaultYesYesGeneral-purpose skills

Add context after the command: /pipeline-failure-triage logs/build-4821.txt. Type /skills to open the skills menu.

Good skill design

  • Push deterministic work into scripts. Parsing a log or querying an API is cheaper and more reliable in a script that returns a summary than in dozens of tool calls.
  • Keep SKILL.md focused. Put long reference material in separate files linked from the steps that need them.
  • Tell it when to stop. Explicit "don't" rules prevent expensive wandering.
  • Review shared skills before installing. Community collections such as github/awesome-copilot and anthropics/skills are useful starting points, but skills can include scripts that run in your terminal.

Instructions, skill, or agent?

They overlap, and it's easy to put everything in one giant instructions file. Answer a few questions about the thing you want Copilot to know or do.

Side by side

Bundles scripts and templatesNoNoYesNoNo
Portable to other agentsAGENTS.md isCopilot-specificYes, open standardPartlyNot loaded by Agent Host sessions

Two more options to know

MCP servers connect Copilot to live systems: a work tracker, a database, an internal API. Use them when the agent needs data it can't find in the repo. Each server adds tool definitions to context, so enable only the ones a task needs.

Hooks run shell commands at fixed points in an agent's lifecycle, such as formatting after every edit or blocking a dangerous command. Use a hook when something must happen every time; instructions are requests, hooks are guarantees.

Common mistakes

  • A 600-line instructions file. Most of it is procedure that belongs in skills. Move it and your every-request cost drops.
  • An agent that's just a prompt. If it doesn't change tools or model, it's probably a skill or a prompt file.
  • A skill with a vague description. "Helps with builds" never matches. "Use when a pipeline or build fails" does.
  • Rules for formatting. Formatters and linters (or a hook) enforce style for free.

Guide 6

Using DESIGN.md

Left alone, agents build the same generic UI everyone has seen. A DESIGN.md at the repo root gives them your colors, type, spacing and component rules as exact values, plus the reasoning behind them.

What it is

DESIGN.md is an open format from Google Labs (it started in Google Stitch) for describing a visual identity to coding agents. It has two layers:

  • YAML front matter with design tokens. These are the normative values: exact hex codes, font sizes, radii.
  • A Markdown body with rationale, organized into ## sections. This tells the agent how to apply the tokens in cases the file doesn't cover.

The format is still at version alpha. The spec and its CLI are changing. Pin the CLI version in CI and re-check the spec when you upgrade.

A starter file

DESIGN.md
---
version: alpha
name: Operations Console
colors:
  primary: "#16202A"
  on-primary: "#FFFFFF"
  accent: "#0E7C86"
  warning: "#B7800F"
  neutral: "#F3F5F4"
typography:
  h1:
    fontFamily: Hanken Grotesk
    fontSize: 2rem
    fontWeight: 700
  body-md:
    fontFamily: Hanken Grotesk
    fontSize: 1rem
rounded:
  sm: 4px
  md: 8px
spacing:
  sm: 8px
  md: 16px
  lg: 24px
components:
  button-primary:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.on-primary}"
    rounded: "{rounded.sm}"
    padding: 12px
---

## Overview
A dense, calm operations tool used for hours at a time. Data first,
decoration never. Color signals state; it is not used for branding.

## Colors
- **Accent (#0E7C86):** the only interactive color. Links, focus, selected rows.
- **Warning (#B7800F):** reserved for states that need attention. Never decorative.

## Layout
Tables are the primary component. Use `spacing.sm` inside cells and
`spacing.lg` between sections. Left-align everything except numbers.

## Components
One primary button per view. Secondary actions are text buttons.

## Do's and Don'ts
- Do show units next to every number.
- Don't use color alone to signal state; pair it with an icon or label.

Sections, in order

Sections can be omitted, but the ones you include must appear in this order: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. Components reference tokens with {path.to.token}, and variants like hover are separate entries (button-primary-hover).

Make Copilot actually read it

Copilot doesn't load DESIGN.md automatically. Wire it in with a scoped instructions file so it's read only when UI is being touched, not on every backend request:

.github/instructions/ui.instructions.md
---
description: 'Use when building or changing any UI, styles, or components.'
applyTo: 'src/Web/**/*.{tsx,css,scss}'
---
* Follow [DESIGN.md](../../DESIGN.md) strictly. Use its tokens; never invent colors,
  font sizes, radii or spacing.
* If a design need isn't covered by DESIGN.md, say so in your summary instead of guessing.
* After UI changes, run `npm run design:lint`.

For heavier UI work you can pair it with a ui-builder skill that includes component templates, or a custom agent restricted to the frontend folder.

Lint it, diff it, export it

The CLI validates structure, catches broken token references and checks WCAG contrast on component color pairs.

terminal
# Validate (exit code 1 on errors)
npx @google/design.md lint DESIGN.md

# Compare versions in a PR
npx @google/design.md diff DESIGN.md DESIGN-next.md

# Generate Tailwind v4 theme variables from the tokens
npx @google/design.md export --format css-tailwind DESIGN.md > theme.css

On Windows and PowerShell, the .md in the command name can collide with the Markdown file association. Use the dot-free alias: npx -p @google/design.md designmd lint DESIGN.md, and designmd in package.json scripts. If npm reports no versions, your registry mirror may not carry the package yet.

A workflow that holds up

  1. Have a designer (or you) write DESIGN.md from the real CSS or Figma values. Agents can draft it from an existing stylesheet; review every value.
  2. Export tokens to your CSS or Tailwind theme so code and doc share one source.
  3. Add the scoped instructions file above.
  4. Run lint in the pipeline; run diff on pull requests that touch DESIGN.md.
  5. When an agent's output drifts, fix the file, not just the component. Add the missed rule to Do's and Don'ts.

Guide 7

Watching and minimizing AI credits

Since June 1, 2026, Copilot bills by tokens, not by request. A quick question on a light model costs a fraction of a credit; a long agent session on a frontier model can cost hundreds. Your habits decide which.

How billing works now

  • 1 AI credit = $0.01. Credits replaced premium requests.
  • You pay for tokens: input (everything sent to the model, including history, instructions and tool output), output (what it writes, including thinking), and cached input (reused context, priced lower). Each model has its own per-token rate.
  • Free on paid plans: code completions and next edit suggestions. Chat, agent sessions, CLI, cloud agent and code review consume credits.
  • Business and Enterprise credits are pooled across the organization. A heavy user draws down everyone's allowance.
  • Budgets are hard stops. If you hit a user-level budget, credit-consuming features are blocked until the next cycle or an admin raises it. There's no automatic fallback to a cheaper model. Completions keep working.

Allowances change. Per-seat allowances and model rates are set by GitHub and have already been adjusted more than once. The promotional allowances for existing Business and Enterprise customers ended September 1, 2026. Ask your Copilot admin for your organization's current pool and budgets, and see the GitHub billing docs.

The biggest driver: input tokens

Every turn in a session re-sends the conversation so far. By turn 20 of an agent session, each new message may carry tens of thousands of tokens of history, file contents and tool output. That's why the habits below mostly reduce input.

Habits that cut cost

Choose the model on purpose

  • Use auto model selection as a default; it routes simple requests to efficient models. Guide 8 covers choosing a model by task.
  • Don't use a frontier reasoning model to rename a variable. Don't use a weak model for architecture either; retries and rework cost more than getting it right once.
  • Pin models in custom agents: strong model for the Planner, efficient model for bounded implementation.
  • Leave thinking effort at its default unless the problem is genuinely hard. Thinking tokens are output tokens, the expensive kind.

Keep sessions short and focused

  • New task, new session. Don't let an unrelated conversation ride along.
  • Use /compact when a long session is still on the same task. Add focus: /compact keep the API design decisions.
  • Use /fork to explore an alternative rather than re-explaining everything in a new session.
  • Plan first. A wrong approach discovered at turn 25 is the most expensive outcome there is.

Send less context

  • Attach the specific files, the error, and the success criteria. Precise grounding avoids broad searching.
  • Exclude noise: .gitignore keeps build output out of the index and search; search.exclude hides logs and generated files from agent search; files.exclude hides them entirely. Search snippets count toward context even if the file is never opened.
  • Keep always-on instructions short. Every line is paid for on every request. Move procedures into skills.
  • Turn off MCP servers and tools the task doesn't need (Configure Tools in the chat input). Each tool definition is input.

Move loops out of the conversation

  • Repetitive query-inspect-query cycles add every intermediate result to context. A script that runs the batch and prints a summary is cheaper and more reliable.
  • Bundle those scripts into skills so everyone uses them.

Measure before you standardize

  1. Pick a representative task and run it a few times (output varies).
  2. Record quality, credits, duration and tool calls from the debug logs.
  3. Change one variable: the model, the tools, the grounding, or delegation.
  4. Keep the cheapest configuration that still meets your quality bar, and revisit when models change.

Code review can bill twice. Copilot code review on github.com consumes AI credits for the model and GitHub Actions minutes for the run. Worth knowing before enabling it on every pull request.

Guide 8

Choosing a model

The model picker lists dozens of models, and they aren't interchangeable. Some are fast and cheap, some reason carefully through large codebases, and the per-token price can differ by as much as 100 times. Match the model to the job, not to habit.

What actually differs

  • Reasoning depth. Stronger models hold more constraints in mind, plan across files and recover from their own mistakes. Lighter models are fine when the answer is local and obvious.
  • Agentic stamina. Long agent sessions need a model that keeps calling tools correctly for dozens of turns without drifting. This is where the top tier earns its price.
  • Speed. Light models answer in a second or two. That matters when you're iterating in inline chat.
  • Context window. Some models offer a 1 million token extended context, billed at a higher long-context rate. Most tasks don't need it; attaching the right files beats attaching everything.
  • Price per token. Input, cached input and output are each priced per model (guide 7). Output is typically 5 to 10 times the input rate, and thinking counts as output.

Price per token isn't price per task. A cheap model that needs three attempts and a manual fix costs more, in credits and in your time, than a stronger model that gets it right once. Pick the cheapest model that reliably succeeds at the task.

Which model for which job

Documentation

Fast and light, or balanced for docs people rely on

READMEs, docstrings, comments, release notes, explaining what a file does. Most of this is summarizing code you point at, which light models do well. Two exceptions justify the balanced tier: architecture or onboarding docs that have to read and connect many files, and anything customer-facing where tone and accuracy matter.

  • Docstrings and comments: select the code, Ctrl+I, light model.
  • Release notes and changelogs: a skill with a template (guide 4) on a light model beats a stronger model guessing the format.
  • Docs input is mostly code you attach, so it's input-heavy. Models with low input rates stay cheap even when you attach several files.
  • Always check facts: commands, flags and version numbers. Every tier invents plausible-looking ones.

Small code changes

Auto, or a light model; step up to balanced if it misses

A bug fix in one function, adding a parameter, a unit test for existing code, renaming across a few files. The change is bounded and you can see the whole thing in one diff.

  • Start with Auto. It routes simple requests to efficient models, and paid plans get a discount for using it.
  • Give exact context: the file, the error, the expected behavior. With good grounding a light model is usually enough.
  • If the first attempt is wrong, fix the prompt once. If the second is wrong too, switch to a balanced model; don't keep retrying the cheap one.
  • Leave thinking effort at its default or lower. Extra reasoning on a small change is mostly wasted output tokens.

Large, complex code changes

Deep reasoning to plan, balanced to build, deep reasoning to review

New features across layers, refactors, migrations, debugging problems that span services, anything where a wrong early decision is expensive. Don't run the whole task on one model. Split it:

  1. Plan with a deep-reasoning model in the Plan agent. It reads widely and makes the design decisions. Correct the plan before any code is written.
  2. Implement each step of the plan with a balanced model. The steps are now bounded, so the expensive reasoning is already done.
  3. Review the result with a deep-reasoning model in a fresh session, focused on the diff.

Custom agents with handoffs (guide 3) make this a repeatable workflow: pin the strong model in the Planner and Reviewer, and the balanced one in the Implementer.

  • Reserve the long-horizon tier for work that genuinely runs for hours or has to search a very large codebase. Its rates are roughly five times the balanced tier.
  • Raise thinking effort for the planning step, not for implementation.
  • Use the 1M-token context only when the task truly needs it. Long-context rates are higher on every turn.

How to set the model

  • Model picker in the chat input: applies to the current session. Hover a model to see its rate.
  • Auto: lets Copilot choose per request. A good default for small, mixed work.
  • Custom agents: model: in the .agent.md front matter pins a model, or a list tried in order, for that role (guide 3).
  • Thinking effort: set in the picker on models that support configurable reasoning. Higher effort means more output tokens.
